## 1. الرؤية المعتمدة للتصميم

منصة جذور المركزية تستضيف **بوابات عائلية مستقلة بصريًا وتحريريًا** لكل عشيرة/عائلة، مع قاعدة نسب موحدة وإدارة ومصادر وصلاحيات لا تتكرر. تظهر بوابة الزعبي كأنها موقع كامل مختص بالزعبي لا صفحة فرعية في موقع عام. تبقى الهوية المركزية لجذور واضحة في التذييل أو قسم التعريف، دون ازدحام بهوية المنصة المركزية في ترويسة بوابة العائلة.

**المثال التصميمي للنطاق:** `al-zoubi.juthoor.dopamind.cloud` — **مقترح غير مفعّل** يحتاج تحقق DNS/TLS وتهيئة Route/Host وDomain Mapping. الرابط الحالي `/al-zoubi` يظل صالحًا ويتحول إلى Canonical Redirect بعد إثبات نجاح البوابة الجديدة. يحتفظ نطاق `juthoor.dopamind.cloud` بالبحث العام واكتشاف العائلات والشجرة الجامعة المشتركة عبر العائلات عند اعتمادها.

> صور «أصولنا» المرفقة مراجع UI/UX وليست اسمًا جديدًا للمنصة؛ العلامة المعتمدة في هذا التصور هي «جذور». ولا تنقل أرقام أو أسماء أو صور تخيلية من المراجع إلى بيانات الإنتاج.

## 3. خريطة المعلومات (Information Architecture)

**المركزية `juthoor.dopamind.cloud`:** الرئيسية العامة؛ اكتشف العائلات؛ بحث الأنساب؛ الشجرة الجامعة المشتركة المعتمدة؛ تسجيل الدخول؛ عن جذور؛ المنصة والإدارة العامة.

**بوابة `al-zoubi.juthoor.dopamind.cloud` المقترحة:**

1. **الرئيسية (Landing):** Hero بصورة تراثية ملائمة، بحث، CTA للشجرة، عدادات محددة بوضوح، موجز أفخاذ، آخر أخبار معتمدة، تاريخ، صور مضافات، شخصيات، دعوة لتقديم معلومة.
2. **الشجرة الجامعة:** عرض جميع الأسماء المنشورة والأبناء، toolbar، بحث عربي، minimap، Fullscreen، zoom/pan، focus، الأجداد والذرية، layout للشريط الأحادي، شارات ذات ألوان/نصوص قابلة للتحكم.
3. **الأفخاذ والفروع:** فهرس هرمي + صفحة مستقلة لكل فخذ وروابط للشجرة الفرعية من الجذور مرورًا بمؤسسه إلى ذريته؛ tabs: نظرة عامة، الشجرة، التاريخ، الدواوين، الشخصيات، الأرشيف، الأخبار، الأعداد. خيار `هذا المستوى فقط / مع الفروع التابعة` عام.
4. **التاريخ والأرشيف:** تبويبات التاريخ العام، النشأة، روايات مختلفة، الهجرات، المدونة/المقالات، المصادر، الوثائق والوسائط.
5. **الدواوين والمضافات:** قائمة وخرائط؛ الصورة، الاسم، التبعية، العنوان العام المأذون، المنطقة، الوصف، الاتجاهات والوسائط.
6. **دليل السند:** محرك بحث مرن حسب العمل والتخصص والمهارات والجامعة والجهة والمنطقة والفخذ؛ ملف طوعي؛ طلب تواصل بحسب إعدادات الشخص؛ تبويبان «سير شبابنا» و«أبحث عن موظف» واجهات فقط.
7. **الأخبار والمناسبات:** عاجل، وفيات/عزاء، عام، الأفراح، نجاح/تخرج، فعاليات وتقويم؛ اقتراح خبر، مرور على مسؤول الأخبار، نشر الموقع بعد الاعتماد.
8. **شخصيات وإنجازات:** قوائم بمصادر وفئات حيادية مع تنويه عدم الحصر.
9. **المبادرات والرد السريع:** تصور أولي فقط ضمن «مجتمعنا» دون ادعاء تشغيل خدمة.
10. **عن العشيرة / المشاركة:** البيانات العامة والتواصل الرسمي، إرسال تصحيح موثق، رابط الإدارة للعضو المخول.

## 4. قواعد صفحة الفخذ

- نفس مصدر البيانات والخدمات والمكونات، لا صفحة مستقلة ببيانات منسوخة.
- افتراضيًا تعرض المباشر والمسموح من جميع الفروع التابعة؛ Toggle للمباشر فقط.
- تعرض شجرة الفخذ مع **خط الأجداد السابق للمؤسس** وذريته المنشورة.
- الإحصاءات نوعها واضح (سجلات الأشخاص المنشورة أو الموثقة). لا تُعرف نسبة شمول السكان دون تعداد مستقل موثق.
- المضافات المشتركة والأشخاص والأخبار تظهر مرة واحدة باستخدام IDs فريدة.
- التعديل يتم بحسب **مالك المحتوى** ونطاق المسؤول؛ لا سلطة مدير فخذ على محتوى عشيرة عام بمجرد ظهوره لديه.

## 5. مواصفات الشجرة الرئيسية

### عناصر العرض

- **Dual layout:** (أ) سلسلة الأجداد السابقين للتشعب في صفوف/شريط أفقي مضغوط يجمع الفروع أحادية الابن بصريًا دون حذف أشخاص، (ب) شجرة متفرعة متوازنة عند بداية التشعبات الرئيسية.
- الحفاظ على **كل اسم وبيان نسب منشور** وفق قواعد الخصوصية، مع Progressive loading للأشجار الكبيرة، وتحميل بصري افتراضي غير محذوف؛ يتم طيّ الرسم لا حذف المعلومات.
- مؤسس القبيلة والعشيرة والفخذ والفخذ الفرعي أكبر واسم الكيان يظهر داخل العقدة / tooltip؛ Desktop hover وMobile tap.
- جدول lookup القائم `person_attributes` مصدر اللون والوصف والتفعيل؛ لا تُزرع ألوان hard-coded بعكس جدول الإدارة. حالات توثيق النسب لا تساوي «شخصية مشهورة».
- شارات أمثلة: نبي، صحابي، سبط النبي، خليفة، جد قبيلة، جد عشيرة، مؤسس فخذ، مؤسس فخذ فرعي؛ **إثبات الإسناد التاريخي شرط مستقل**.
- Legend دائم مع تسميات/أيقونات بجانب الألوان لسهولة الوصول، وأوضاع تخفيض الحركة، وضع الطباعة عند الحاجة.
- التفاعلات: Zoom ±، fit، full-screen، mini-map، search، focus، show ancestors، show descendants، back، breadcrumbs.
- صفحة شجرة الفخذ لا تنشئ Person جديدًا ولا تنسخ الرسم أو تعدل parentage.

## 6. تصميم Admin الجديد

**Family Workspace:** Overview؛ بوابة العائلة والهوية البصرية؛ أسماء العائلة والنطاق؛ شجرة وإحصاءات؛ المؤسسون والفروع؛ الأخبار والنعي (مع مراجعة حساسة)؛ المضافات والخرائط؛ التاريخ والمصادر؛ الأرشيف والصور؛ الشخصيات؛ دليل السند؛ الموافقات؛ الأعضاء والأدوار؛ سجل التدقيق؛ الإعدادات.

**Entity/Fakhd Workspace:** نفس المحتوى مع نطاق صلاحيات متفرع واضح واسم الفخذ ظاهر أعلى الصفحة. لا تكشف صفات أو أرقام شخصية مقيدة.

**Platform Super Admin:** مركزية إدارة العائلات، إضافة Family، Domain verification، الحوكمة، الصلاحيات، Taxonomies/attribute colors، الروابط المشتركة وتدقيق الأنساب، صحة المنصة. مختلفة بصريًا عن صفحة العائلة.

**محرر البوابة:** الشعار والغلاف والصورة الافتراضية وترتيب الأقسام وتفعيل/إخفاء الأقسام المتاحة وCTA ولونًا محدودًا ضمن نظام التصميم، مع Preview قبل النشر وRollback للتغييرات؛ لا تسمح بحقن HTML/JS.

## 7. بنية نطاقات العائلات — مسودة ADR-011

- ربط host موثوق بـFamily ID باستخدام سجل/domain mapping مع حالة التحقق؛ fallback عبر path أثناء الهجرة.
- يطبّق **Tenant/Family Context** على كل query العام؛ قواعد النسب المشتركة تظل ضمن سياق نشرها مع السماح بروابط مقتصدة للأجداد المعتمدين فقط.
- wildcard DNS أو records صريحة، wildcard TLS أو شهادة تغطي المضيفين، HTTPS/HSTS، منع Host header confusion، حجز أسماء المنصة الحساسة (`www`, `api`, `admin`, `login`, `static`...).
- حماية جلسات الدخول وكوكيز المركز والعائلة وتفويض طلبات إدارة العائلة عند وجود أكثر من subdomain؛ لا صلاحية تنتقل بين العائلات.
- Canonical SEO وsitemap per-family، redirect 301 فقط بعد الجاهزية والمراجعة، ضبط analytics privacy.
- فصل CSS branding المحدود عن permission rules. لا تفرض Frontend subdomain على Core Admin/API إن تعارض مع أمان الجلسات.
- قبل إنشاء migration فحص هيكل الجداول الحالي والخدمات القائمة بدل افتراضها.

## 8. سياسة المحتوى والمسؤولية

- الأخبار والوفيات والعزاء: تقديم → تحقق مصدر/موافقة → اعتماد مسؤول مخول → نشر؛ المنشور يصل مباشرة للموقع بعد الاعتماد عند عدم وجود وقت نشر مستقبلي، والتغييرات الحساسة تحفظ سجلها.
- Facebook المؤجل: **لا live feed أو Meta API**. تصميم صندوق لمصدر فيسبوك الرسمي مع روابط منشورات معتمدة مدخلة يدويًا فقط إلى حين إقرار التكامل.
- دليل السند: Privacy by default، Opt-in، تحكم بإظهار الحقول والاتصال، لا فهرسة رقم الهاتف، اتصال بالواسطة اختياري.
- السير الذاتية/طلب الموظف: **UI only مع تعطيل submit/رفع الملفات**؛ قبل التفعيل يلزم retention/privacy/consent/role approval وCV matching عبر اختيار المرشح.
- مبادرة الرد السريع: واجهات محتوى وتواصل رسمي فقط، **لا نظام استغاثات/خدمة طوارئ** دون وثيقة حوكمة منفصلة.
- الأرقام والصور في التصميم demonstrative وليست حقائق إنتاجية؛ تفاصيل الأشخاص الفعلية تخضع لقواعد النشر.

## 10. معايير قبول إلزامية

1. لوحة الزعبي تعرض محتوى الزعبي فقط؛ صلاحيات وطلبات HTTP لعائلة أخرى ترفض حتى مع URL معدل أو Host مزوّر.
2. البحث العام منفصل عن بحث العائلة، وكل بيانات الأحياء غير المنشورة مخفية في HTML/JSON/القوائم/العدادات/التصدير.
3. الشجرة تحتفظ بجميع الأشخاص المنشورين والعلاقات دون مسح تلقائي لذوي الابن الواحد؛ المعروض المضغوط expandable.
4. شارات الشخص تجلب وصفها ولونها وتفعيلها من lookup، مع Legend وتباين وإظهار نصي؛ مؤسس الفخذ يظهر بعنوان الفخذ ووصفه في hover/tap.
5. إحصاءات «الفخذ الأكبر» تستخدم سجلات فريدة ذات نطاق/تاريخ محدد، **وليست عدد السكان الحقيقي**.
6. المحتوى الموروث لا يكرر السجلات، ومحرر الفخذ لا يستطيع تعديل سجل لا يملكه.
7. الأخبار والوفيات والأفراح لا تظهر قبل المراجعة، ولا يتجاوز Frontend-only للوظائف والسير الذاتية مرحلة التصميم.
8. صور المضافات/الأرشيف تستخدم MediaAccess والتحقق من الحقوق، ولا تكشف أصل الصورة المقيد.
9. كل التعديلات UI/route تتبع اختبارات Phase 1–4 ولا تغيّر APIs أو خدمات النسب بلا داعٍ.
10. الواجهة لا تستخدم «أصولنا» كشعار إنتاج؛ أمثلة التصاميم تظل مراجع بصرية فقط.

## 10.1 ملاحظة مستودع إضافية قبل التعديل

في أحدث Commit مقروء من GitHub (`53a81cff`)، أُضيف ملف `.htaccess` في جذر المستودع يتضمن **قاعدتي Rewrite متماثلتين** إلى `public/$1`، وتعليمات `Options All` ومسار سجل PHP. هذه ملاحظة فحص كود لا دليل على حصول خلل تشغيلي؛ لكنها تستحق **مراجعة أولوية P0 قبل تهيئة نطاقات العائلات** لتجنب تكرار `/public` أو كشف ملفات حساسة أو سجلات. يُراجع ملف إعداد الخادم الفعلي وDocumentRoot على البيئة المنشورة قبل اعتماد أي تغيير؛ لا تُطبّق إصلاحات افتراضية دون اختبار.

كما أظهر GitHub Commit `f3e38a4` ملفات Phase 4 (أخبار، مناسبات، دليل)، وبالتالي تُعامل هذه المجالات بوصفها وظائف موجودة في كود المستودع المقروء مع ضرورة التحقق من تشغيلها وربطها بالبوابة، لا بوصفها نظامًا يجب إنشاؤه من الصفر.
