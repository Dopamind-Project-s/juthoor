# جذور — ملحق أولويات التنفيذ المعتمد P0

**التاريخ:** 27 أكتوبر 2026  
**الحالة:** متطلبات معتمدة للخطة؛ **لا تعني أنها نُفذت برمجيًا**.  
**المرجعية:** متطلبات v2.0 (الأساس الرسمي) + تجربة v3.0 (مرجع التصميم) + تدقيق السيدرز بتاريخ 27 أكتوبر 2026 + قرارات المحادثة الحالية.

## P0-A — تحسين إضافة الأشخاص وتعديلهم ومراجعتهم (الأولوية الأولى)

**الهدف:** إدارة النسب بسرعة وأمان من داخل الشجرة، وليس عبر نماذج معقدة منفصلة.

- إجراءات مباشرة من عقدة الشخص: **إضافة ابن، إضافة أب عند الحاجة، تعديل الشخص، اقتراح تصحيح، مراجعة المصادر، فتح صفحة الشخص**، بحسب الصلاحيات.
- إضافة ابن من عقدة الأب تُدخل مرجع الأب تلقائيًا مع إظهاره للمستخدم وإمكانية التراجع قبل الحفظ؛ **لا تعتمد نسبًا غير موثق تلقائيًا**.
- بحث عربي قبل الإنشاء، مع اختلافات الإملاء والاسم المركب، والتنبيه إلى الأشخاص المحتمل تكرارهم مع عرض نسبهم؛ لا دمج تلقائي.
- نموذج متدرج: (1) الاسم والهوية (2) صلة القرابة (3) المصدر/الثقة (4) الخصوصية وحالة الحياة (5) مراجعة ملخص التغيير.
- خيارات `living/deceased/unknown` واضحة، وحماية بيانات الأحياء والمجهولين، وخصوصية الحقول كما في `PersonPrivacy`.
- مراجعة مقارنة **قبل/بعد**، إظهار الشخص والأب والفرع المتأثرين، مبرر القرار، المصدر، مقدم الطلب، وموافقات المراجعين المؤهلين.
- اختلافات الأبوة والروايات تُسجل Assertions مستقلة؛ لا تغير الرسم البياني الفعّال قبل الاعتماد.
- إظهار أثر تغيير الأب أو المؤسس على الفروع والأشجار المرتبطة؛ منع الدورات والعلاقات المتناقضة والتعديل العابر للعائلات دون مراجعة مشتركة.
- UX عربي RTL متوافق مع الهاتف؛ دعم اختصارات/إضافة متتابعة لأبناء نفس الأب دون إعادة اختيار الأب، مع حفظ مسودة آمن.
- اختبارات Laravel وBrowser لعمليات الإضافة/التعديل/المراجعة/رفض الطلب/إلغاء العملية، وعدم تسريب حقول محجوبة أو تكرار Person.

**معايير القبول:** إضافة ابن من الشجرة بحد أدنى من الخطوات؛ تحذير تكرار قبل الحفظ؛ أي تعديل حساس يمر بالمراجعة؛ لا تغيير في نسب معتمد أو منشور دون الصلاحيات والموافقة؛ كل عملية مدققة وقابلة للتتبع.

## P0-B — تحسين الأدوار والصلاحيات وRole Seeder (بالتوازي مع P0-A)

**مبدأ:** الصلاحيات دقيقة، ومحددة بالنطاق `platform/family/entity/branch`، ولا تنتقل تلقائيًا من فخذ إلى عشيرة أو من عائلة إلى أخرى.

| الدور المقترح | النطاق | الحد الأدنى من المسؤوليات |
|---|---|---|
| Platform Super Admin | المنصة | إعدادات المنصة والعائلات والسياسات والأدوار العامة؛ عمليات النسب الحساسة تظل مدققة |
| Family Admin | عائلة | إدارة أعضاء العائلة، تفويض المسؤولين، الموافقة ضمن صلاحيات العائلة |
| Genealogy Curator | عائلة أو فخذ | تنسيق الأنساب، إدارة المصادر، رفع طلبات التصحيح، مراجعة محددة بالتفويض |
| Genealogy Editor | عائلة أو فخذ | إضافة الأشخاص واقتراح التعديلات؛ **لا يعتمد طلبه بنفسه** |
| Genealogy Reviewer | عائلة أو فخذ | مراجعة الأنساب والمصادر؛ فصل واجبات التحرير والموافقة |
| Content Manager / Editor | عائلة أو فخذ | تحرير المحتوى والأرشيف والدواوين بحسب الملكية |
| News Editor | عائلة أو فخذ | إعداد الأخبار والمناسبات وإرسالها للمراجعة |
| News Approver | عائلة أو فخذ | اعتماد الأخبار؛ النعي يتطلب تحققًا إضافيًا |
| Directory Moderator | عائلة | الإشراف على طلبات الدليل الطوعي دون كشف حقول اتصال مقيدة |
| Family Member / Reader | عائلة | القراءة وفق قواعد النشر والخصوصية؛ إرسال مقترحات عند السماح |
| Public Visitor | عام | السجلات والمحتوى المنشور فقط، دون عضوية ضمنية |

**توجيه:** هذه **أدوار مقترحة** وليست أسماء جداول مفروضة. افحص RBAC الحالي وSpatie أو الآلية الموجودة، ثم أعد استخدامه؛ لا تنشئ نظامًا موازيًا.

**Role Seeder:** إنشاء/تحديث معرفات الأدوار والصلاحيات بطريقة idempotent، مفاتيح ثابتة، versioned permission catalog، عدم مسح منح المستخدمين الحالية، عدم استبدال أدوار معدلة إداريًا بصمت، diff + dry-run قبل ترقية الأذونات، وفحص least privilege. فصل `person.create`, `person.propose-update`, `person.review`, `person.publish`, `relationship.change`, `founder.change`, `source.manage`, `family.members.manage`, `news.review`, `privacy.manage`, `audit.read`, `role.assign` مع policy/scope gates. لا يكفي اسم الدور وحده دون تحقق Family/Entity ownership.

**معايير القبول:** اختبارات permission matrix (allow/deny) لكل دور ولكل نطاق، منع self-approval، منع التصعيد الأفقي والعمودي، حفظ منح الأدوار عند إعادة تشغيل Seeder، وعدم ظهور أزرار لا يحق للمستخدم تنفيذها مع التحقق في Backend أيضًا.

## P0-C — اعتماد Seeders كاملة لكل عائلة (بعد تثبيت ضوابط P0-B)

- **Family seed package** موحد لكل عائلة: manifest/version/checksum، family metadata، tree/root references، branches/parent hierarchy، founder links، people stable IDs، relationships، sources/citations، privacy/living statuses، publication/review state، attributes، optional content references.
- حالات `verified / sourced / disputed / pending / unknown` صريحة؛ **وجود سجل في Seeder لا يجعله معتمدًا تاريخيًا**.
- فصل `reference dataset` عن `demo fixtures` وعن `production bootstrap`. لا تنشر fixtures التجريبية.
- preflight validation + dry-run report + conflict detection + idempotency + transactional import + source audit، مع عدم إعادة كتابة بيانات عُدلت يدويًا.
- دعم `family:seed-audit` و`family:seed --family=... --dry-run` أو ما يناسب بنية المشروع الحالية بعد تدقيقها؛ لا تضف CLI مكررًا.
- استيراد القواسمة وROOT variants يبقى مراجعة لا تصحيحًا آليًا؛ **39 اختلاف اسم** و**34 قواسمة قيد المراجعة** لا تُعتمد آليًا.
- شجرة الأشخاص **موحدة بلا تكرار** بين العائلات، وارتباط فخذ/عشيرة يمثل view أو membership محسوبة، لا Person مكررًا.
- تقرير اكتمال لكل عائلة: الأشخاص، الفروع، المؤسسون، الروابط، المراجع، نسب غير محسومة، حقول خاصة، إحصاءات المنشور فقط؛ لا تسوّق التقرير كتعداد السكان.
- اختبار إعادة التشغيل مرتين على SQLite/PostgreSQL، وحماية أسماء الأشخاص والأبوة والـ verification والخصوصية والمحتوى المعدل إداريًا.

**معايير القبول:** يمكن إضافة عائلة جديدة بحزمة seed واضحة وقابلة للمراجعة، مع الحفاظ على البيانات الموجودة؛ كل شخص وعلاقة لهما مصدر وحالة إثبات واضحة أو علامة نقص؛ لا duplicates ولا cross-family leakage.

## ترتيب الخطة المحدّث

1. **P0-A + P0-B**: إدارة الأشخاص من الشجرة، والمراجعات، ومصفوفة الأدوار والصلاحيات وSeeder الخاص بها.
2. **P0-C**: تدقيق Seeders العائلات وتصحيحها واعتماد حزم الاستيراد وبيانات المصدر بعد مراجعة بشرية.
3. **UX-00/01**: جرد وتثبيت نظام التصميم وواجهات Figma بناء على البيانات والـ workflows الحقيقية.
4. **UX-02…09**: بوابات العائلات والشجرة والفروع والأرشيف والدليل والأخبار ولوحات الإدارة والاختبارات، مع إعادة ترتيب UX-08 لتقديم شاشات إدارة الأشخاص والأدوار مبكرًا.
